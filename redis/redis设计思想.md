# 主从复制
* 关键词：RDB、偏移量、复制积压缓冲区。
* 主从复制的本质是数据的冗余备份。它把一台机器上的数据，完整地克隆到其他机器上。

## 1.核心流程：三次握手（建立连接）
就像我们打电话要先拨号、确认信号、说话一样，从节点连接主节点也有一套标准化流程，
这在源码里是分状态流转的：  
* 保存主节点信息：从节点配置文件里写了 replicaof 192.168.1.1 6379，
从节点启动后，就会先把主节点的 IP 和 Port 保存起来。  
* 建立 Socket 连接：从节点创建一个 socket，尝试连接主节点。
* 发送 PING：连接建立后，从节点发一个 PING 命令。
  * 目的：检查主节点是否存活，或者网路是否通。
  * 响应：主节点返回 PONG。如果返回错误（比如正在忙于载入 RDB），从节点会断开重连。
* 认证：如果主节点设置了 requirepass，从节点必须发 AUTH 密码。
* 发送端口：从节点告诉主节点：“嘿，我监听的端口是 6380，你在日志里记录一下，方便以后管理。”
* 同步：从节点发送 PSYNC 命令，正式开始数据同步。

## 2.数据同步：三种模式的演进
这是主从复制最复杂的部分，经历了三个版本的迭代，目的是更快且断线重连后更少数据丢失。

### 模式一：全量复制
* 场景：第一次连接，或者数据差距太大。
* 过程：
  * 主节点收到 SYNC，后台执行 bgsave，生成最新的 RDB 快照文件。
  * 主节点将 RDB 发送给从节点。
  * 从节点清空自己旧数据，加载 RDB。
  * 问题：这期间主节点来写操作怎么办？主节点会用一个 Replication 
  Backlog Buffer（复制积压缓冲区） 记录这些新写操作。
  * RDB 发完，主节点把缓冲区里存的新增修改发给从节点。
* 代价：非常消耗 CPU、内存（fork 消耗）、网络带宽。

### 模式二：增量复制
* 场景：从节点断线重连，且断开时间不长。
* 核心机制：复制积压缓冲区。
* 原理：
  * 这个缓冲区是一个定长环形队列（默认 1MB）。
  * 主节点每个写命令不仅发给从节点，还会往这个队列里塞一份。
  * 从节点重连时，告诉主节点：“我断开前的偏移量是 1000”。
  * 主节点一看：“我现在的积压 buffer 里还有 800 到 2000 的数据”。
  * 主节点直接把 1000 之后的数据扔给从节点，不用重传整个 RDB。
* 失败情况：如果断开太久，偏移量的数据已经被新数据覆盖出缓冲区了，就只能退化回全量复制。

### 模式三：无盘复制
* 场景：主节点磁盘慢，不想生成 RDB 文件到磁盘。
* 原理：主节点 bgsave 生成的 RDB 数据不再存盘，而是直接通过 socket 流式发给从节点。
* 代价：网络拥塞会更明显，但节省了主节点磁盘 IO。

# 哨兵模式
* 关键词：主观下线、客观下线、Raft 选举、故障转移。
* 如果把主从复制比作“国王和秘书”，那哨兵就是“摄政王”或“内阁”。国王（主节点）倒下时，
谁来主持大局？是哨兵。

## 1.核心架构
* 哨兵节点：独立运行的 Redis 进程，不存数据，只干监控、选主的活。 
* 数据节点：就是平时的 Master 和 Slave。 
* 组成：通常运行 奇数个（3、5、7）哨兵节点，形成哨兵集群，防止单个哨兵自己挂
了或者判断失误。
## 2.三个监控阶段
哨兵对主节点的下线判断是有层次的，就像法庭判决，先怀疑，再定罪。

### 主观下线：
* 单点视角：哨兵 A Ping 主节点，超过 down-after-milliseconds（默认 30秒）没回音，哨兵 A 就在脑子里标记主节点为 S_DOWN (Subjectively Down)。
* 含义：“我觉得你挂了”。
### 客观下线：
* 集群视角：哨兵 A 不想冤枉主节点，它去问哨兵 B、C、D：“你们觉得主节点挂了吗？” 
* 如果有 Quorum（法定人数） 个哨兵（比如 5 个里要有 2 个同意）都认为挂了，哨兵
A 才会把主节点标记为 O_DOWN (Objectively Down)。
* 含义：“大家都觉得你挂了，这事儿确凿了”。
### 领导哨兵选举：
主节点确实挂了，谁来执行故障转移？不能大家都去操作，乱套了。
* Raft 算法简化版：所有哨兵开始投票。先给自己投一票，然后问别人：
“选我当 Leader 行不行？”
谁先拿到超过半数（N/2 + 1）的票，谁就是 Leader。Leader 开始干活。
## 3.故障转移
Leader 哨兵选出后，执行以下步骤（这是最惊心动魄的时刻）：

* 选新主：在所有从节点里挑一个最靠谱的。优先级高的（slave-priority 配置）。
数据最新的（replication_offset 最大的）。RunID 字典序小的（防止倾斜）。
* 执行晋升：Leader 哨兵向被选中的从节点发送 SLAVEOF NO ONE。
它从这一刻起变成 Master。
* 改配置：Leader 告诉其他从节点：“别认旧主了，认新主（SLAVEOF 新主IP 新主Port）。”
* 变更门面：原主节点如果复活了，哨兵会把它变成新主的 Slave。
* 通知客户端：哨兵会通过 Pub/Sub 发布订阅消息，告诉连接上来的客户
端：“换老板了，IP 变了，连新的吧。”


# 集群模式
* 关键词：16384 槽、CRC16、MOVED/ASK 重定向、Gossip 协议。
* 集群模式是 Redis 的终极形态，为了解决单机内存不够和单机并发不够的问题。它把一个大 Redis 拆成了很多个 Redis。

## 1.核心概念：哈希槽
这是理解集群的钥匙。不要去想“分库分表”，要想“槽”。  
Redis 创建了 16384 （2^14）个槽位。这些槽位分配给集群中的各个 master 节点。
* 例子：
节点 A 负责：0 - 5000 号槽。
节点 B 负责：5001 - 10000 号槽。
节点 C 负责：10001 - 16383 号槽。
## 2.客户端如何找到数据？（路由）
客户端要存 name="Tom"。  
客户端计算哈希：CRC16("name") % 16384。假设结果是 5050。
客户端查本地的缓存表（槽位映射表）：5050 号槽属于 节点 B。
客户端直接向节点 B 发送请求。  
特殊情况：MOVED 重定向  
如果客户端的缓存表是旧的（比如节点 B 的槽挪走了），客户端发给了节点 B。
节点 B 会回包：-MOVED 5050 192.168.1.5:6379（这槽现在归 C 了）。
客户端收到后，更新本地缓存，下次就去找 C 了。

## 3.集群的高可用（内置哨兵）
集群模式不需要额外搭哨兵，因为它把哨兵的逻辑写进了节点代码里。

监测：节点之间每秒互发 PING。  
投票：如果半数以上主节点认为某主节点挂了（PFAIL -> FAIL），就标记为下线。  
选举：该主节点的从节点们发起投票，选一个新主，接管那批槽位。  
注意：这是从节点投票选自己，跟哨兵模式（哨兵节点投票选哨兵 Leader）略
有不同，但逻辑类似。  
## 4.扩缩容：数据迁移
这是集群模式的杀手锏。如果想加一个节点 D：

* 分槽：把节点 A 的 1000 个槽位挪给 D。
* 迁移状态：
  * 源节点 A 把这些槽标记为 MIGRATING（迁移中）。
  * 目标节点 D 把这些槽标记为 IMPORTING（导入中）。
* 搬数据：
  * 客户端发请求给 A，A 发现 key 属于迁移槽。
  * A 先问 D：“你有这个 key 吗？”
  * 如果有：A 返回 ASK 重定向，让客户端去找 D。
  * 如果没有：A 把 key 的数据取出来，发给 D，存好后，再返回 ASK 让客户端去找 D（这叫原子迁移）。
