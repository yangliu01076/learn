# 0 杂记
尽量少写死一个字段，多考虑一下  
发布上线的每个步骤都要看发布计划  
对于修改配置的操作，一定要等服务发布之后，以免不兼容新增的字段，
同时也要考虑新增字段时，字段为 null 的情况    
对于 == , ! , && 等逻辑符号会涉及到拆箱操作，一定注意对包装类判空   
# 1 修改接口
* 当修改一个方法时，一定要用idea打开usage，看看到底谁在用，以防上游功能出现问题  
* 修改消费消息的逻辑，要打开tiger，看看有哪些消费者  
* 修改涉及面广的逻辑，要考虑发布的兼容性，比如前端，或者上下游  
* 由于业务变动，需要去掉接口的必填校验时，一定要多想一想，检查一
下下游，如果没有这个值，会不会有问题  
* 查询接口新增字段，一定要判空，判断非空才设置查询条件，
避免影响其他业务


# 2 数据库操作
* 不在一个数据库，不能开启事务  
* 当数据库查询入参是个列表时，一定要拦截为空列表的情况，
包括返回数据为空列表的时候也要特殊处理   
* 线上修改操作，推荐设计数据库操作执行的开关，防止误操作，先关闭开关，看看日志
是否符合预期，再开启开关   
* Spring管理事务时，事务上下文和mysql Connection 是存在 ThreadLocal 中的，
因此在同一个事务中，不能切换线程，否则事务会失效；不同线程的未提交修改也是相互
不可见的

# 5 异步
修改基于消息的异步逻辑时，要考虑四种场景，新实例生产-旧实例消费；
新实例生产-新实例消费；旧实例生产-旧实例消费；旧实例生产-新实例消费
