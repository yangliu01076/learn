### Netty 的 Reactor 线程模型是怎样的？为什么说它是“无锁串行化”设计？
Netty 默认采用主从 Reactor 多线程模型。  
BossGroup：专门负责接收客户端的 TCP 连接（OP_ACCEPT）。  
WorkerGroup：负责处理网络读写和业务逻辑。  
无锁串行化精髓：Netty 底层保证一个 Channel 在整个生命周期内，只绑定
到一个 NioEventLoop 线程上。这意味着该 Channel 的所有 I/O 操作和
业务处理都在同一个线程内串行执行，不需要加锁，彻底避免了多线程并发竞争
带来的上下文切换和锁开销，这也是 Netty 能支撑极高并发的底层原因。

### Netty 是如何解决 TCP 拆包和粘包问题的？以 HTTP 协议为例说明。
拆包粘包的本质是因为 TCP 是面向字节流的协议，没有消息边界。  
解决工具：Netty 提供了多种解码器（如定长 FixedLengthFrameDecoder、
分隔符 DelimiterBasedFrameDecoder）。  
HTTP 协议的切分源码：在 Netty 中，HttpServerCodec 负责按 HTTP 协议
规范（\r\n 切分请求行/头，空行区分头部和体）解析字节流。但它产出的是离散
的 HttpRequest 和 HttpContent 碎片。  
聚合器作用：必须搭配 HttpObjectAggregator。它内部会缓存这些碎片，
直到收到 LastHttpContent（标识请求体结束），然后拼接成一个完整的 
FullHttpRequest 向下传递，业务层只需处理完整的 FullHttpRequest 即可。

### ChannelInitializer 为什么能保证初始化逻辑“只执行一次”？
这是 Netty 非常精妙的“自毁式”设计。 ChannelInitializer 是一个特殊的 Handler
，当 Channel 注册到 EventLoop 时，会触发它的 handlerAdded 方法。
在其源码的 initChannel 逻辑中，使用了 ConcurrentHashMap 的 
putIfAbsent 做并发防重保护。更重要的是，在 finally 块中，它执
行了 pipeline.remove(this)，直接把自己从 Pipeline 双向链表中摘
除。脚手架搭完大楼就拆掉，从结构上彻底杜绝了重复执行的可能。  

### Netty 的异步编程机制是怎么实现的？Future 和 Promise 有什么区别？
Netty 所有的 I/O 操作都是异步的。  
区别：Java 原生 Future 是只读的，只能通过 get() 阻塞或 isDone() 轮询。Netty 
的 Future 增加了 addListener 监听器，支持异步回调。而 Promise 继承自 Netty 
Future，它是可写的，提供了 setSuccess() 和 setFailure() 方法。   
应用：底层线程（如 EventLoop）干活前创建一个 Promise 盲盒返回给调用者，调用者
不阻塞，干完活后底层线程调用 promise.setSuccess() 触发回调通知调用者。实现了
跨线程的状态传递。

### Netty 启动时，future.channel().closeFuture().sync(); 这行代码的作用是什么？
核心作用是阻塞主线程，实现进程保活。 Netty 底层的 EventLoop 线程
是守护线程，如果主线程执行完 bind() 就退出，JVM 检测到没有非守护线程存
活会直接退出，导致服务挂掉。closeFuture() 返回一个代表 Channel 关闭
事件的凭证，调用 sync() 会死死阻塞主线程，直到 Channel 被关闭，从而保
证 JVM 进程存活，让 Netty 服务持续监听请求。  

### 什么是 JDK 的 epoll 空轮询 Bug？Netty 源码是如何解决的？
现象：在 Linux 下，由于 JDK 对 epoll 的封装缺陷，当收到异常的 TCP 
连接（如 RST 包）时，Selector.select() 本该阻塞，却会立刻返回 0，
导致 NioEventLoop 陷入死循环，CPU 瞬间飙到 100%。  
Netty 源码解决：Netty 采用“熔断重建”策略。在 NioEventLoop 源码中
，用 selectCnt 记录空等次数。如果连续发生 512 次（默认阈值）无意义的
唤醒，Netty 判定 Bug 触发，调用 rebuildSelector()，创建一个全新的
Selector，把老 Selector 上所有的 SelectionKey 转移到新 Selector 
上，并替换掉老的，从而完美规避底层 Bug。

### Netty 为什么大量使用堆外内存？不受 GC 管控会不会导致 OOM？
为什么用：为了“零拷贝”和极致性能。堆外内存数据直接与网卡交互，
避免了数据在内核态和 Java 堆之间的来回复制，同时减轻了 GC 的压力。  
OOM 风险：会。如果堆外内存发生泄漏，JVM GC 回收了 Java 堆里的包装
类，但底层 C 内存没有释放，最终会导致物理内存耗尽，抛出 
OutOfMemoryError: Direct buffer memory，甚至被 Linux OOM-Killer 杀掉。

### Netty 的引用计数法是怎么工作的？怎么保证 ByteBuf 刚好减到 0？
初始值：Netty 的 Allocator 在分配 ByteBuf 时，底层源码写死初始计数 refCnt = 1。
保证机制：依靠严格的责任链契约。  
自动释放：业务常继承 SimpleChannelInboundHandler，它在 finally 
块中会自动调用 release()。  
兜底释放：如果消息传到 Pipeline 末尾还没被消费，TailContext 会兜底执行 release()。  
出站释放：调用 ctx.writeAndFlush() 将数据写入网卡底层后，HeadContext 会自动释放。  
异常保护：如果计数已经为 0 还有人调用 release()，底层 CAS 操作会抛出 
IllegalReferenceCountException 提前暴露 Bug，防止悄悄泄漏。

### Netty 是如何在生产环境中抓出内存泄漏的？
依靠源码中的 ResourceLeakDetector。 它利用了 Java 的 
WeakReference（弱引用）和 ReferenceQueue（引用队列）。当 
ByteBuf 被创建时，Netty 会创建一个指向它的弱引用。如果业务代码忘
了 release()，JVM GC 时会把 ByteBuf 回收，并将弱引用放入队列。
Netty 后台线程扫描到队列里有对象，就知道“它被 GC 了但引用计数没归零”，
判定为泄漏，并打印出创建时的调用栈。 为了不影响性能，默认采用
SIMPLE 级别（1% 随机采样）。压测时可以开启 ADVANCED 级别记录更
详细的访问轨迹。

### 在 Netty 中，如果连续发送两个 HTTP 请求，为什么可能收不到第二次响应？
因为 HTTP/1.1 是请求-响应模型，且默认支持长连接复用。 如果服务端在返回响应后，直接调
用了 ctx.writeAndFlush(response).addListener(ChannelFutureListener.CLOSE);
底层数据一写完就会立刻掐断 TCP 连接。客户端复用同一个 Channel 
发送第二个请求时就会失败。   
源码级修复：服务端应通过 HttpUtil.isKeepAlive(request) 判断请求头。
如果是 keep-alive，则设置响应头 Connection: keep-alive 并不加 CLOSE 
监听器；如果不是，才写完即关。
